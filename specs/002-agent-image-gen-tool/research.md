# Research: Agent Image Generation Tool

## 1. What actually needs to be shared between `/create-image` and the new tool

**Decision**: Extract only the deterministic, non-LLM-reaction portion of `ConversationController::generateImageMessage` (`app/Http/Controllers/Api/ConversationController.php:327-358`) into a new `App\Services\ImageGenProviders\ImageGenerationService`: resolve the assistant's configured `ImageGenModel` (or fall back to `config('ai.image_gen')`), enhance the raw prompt via the existing `ImageGenPromptEnhancer`, and call the resolved provider's `generate()`. This returns `{enhancedPrompt, imageData}` and does nothing else — it does not create a `Message`, call the reaction LLM, or store the `Image`.

**Rationale**: This is the one piece that is *actually* identical between both callers and is the exact reuse the user asked for. Everything downstream of it legitimately differs by caller (see #2), so pulling the whole `generateImageMessage` method — including the in-character reaction call and message persistence — into a shared class would force one of the two callers to work around behavior it doesn't want, which is itself a smell that the abstraction boundary is wrong.

**Alternatives considered**: Extracting the entire `generateImageMessage` (enhance → generate → react → persist) as one shared method, with the tool calling it and discarding/repurposing the reaction. Rejected: it bills the tool for a second LLM call it doesn't need (see #2) and requires the shared method to accept awkward "am I in a tool context" branching internally — the antithesis of a clean shared abstraction.

## 2. Does the tool need its own in-character reaction call?

**Decision**: No. `generateImageMessage`'s `reactToGeneratedImage` (`ConversationController.php:385-432`) exists because the manual `/create-image` command is a dead end otherwise — nothing else in the request pipeline is going to comment on the image, so the command must synthesize that reaction itself with a dedicated LLM call. The agent-mode tool has no such gap: it executes *inside* `AgentLoopRunner`'s loop, which already re-calls the model after every tool result and lets it write a natural in-character continuation — exactly like it already does after `basic_calculator` or `get_current_datetime` return a result. Firing a second, separate reaction call from inside the tool would be a redundant LLM round-trip producing a second, competing piece of in-character text for the same image.

**Rationale**: Matches how every other tool in this loop already works — the tool returns data, the model (already generating in-character per the existing system prompt) narrates it. Also avoids duplicating `reactToGeneratedImage`'s own moving parts (emotion-tag prompt section, retrieval, conversation history reconstruction) inside a tool class.

**Alternatives considered**: Calling `reactToGeneratedImage` from inside the tool and returning its text as the tool result. Rejected per the above — redundant model call, and the loop's own final answer would still run afterward, producing two competing reactions in the same turn.

## 3. Where does the generated image attach, given the tool has no `Message` to attach it to yet?

**Decision**: The tool creates its own minimal carrier message the moment it generates the image — `$conversation->messages()->create(['role' => 'assistant', 'content' => ''])` — and stores the image on it via the existing `Image::storeFromBase64($imageData, $carrierMessage, $storagePath)` (`app/Models/Image.php`), immediately, inside `handle()`. The tool call's *return value* to the model is a short JSON confirmation (`{"status": "success", "enhanced_prompt": "..."}`), never the image bytes.

**Rationale**: `AgentLoopRunner`'s final assistant message (`ConversationController.php:291-295`) is only created *after* `run()` returns, so nothing exists yet to attach an image to while the tool is executing — the tool must create its own carrier. Doing this immediately, inside `handle()`, rather than stashing the image on tool instance state for the controller to attach afterward, is the simpler of the two: it needs no new state-passing contract between the tool and the controller, and it generalizes for free to a task that generates more than one image (FR-009) — each call just creates its own carrier message, with no special-casing for "the second image in this task." The tool's return value must stay a short confirmation, not the raw image data, because that return value is JSON-encoded three times over — into the next LLM request (`AgentLoopRunner.php:66`), into the persisted `tool_call` message row (`AgentLoopRunner.php:118-121`), and into the `tool_calls` summary sent to the frontend (`ConversationController.php:304`) and rendered by `AgentToolCallsTrace.jsx` via `JSON.stringify`. Embedding base64 image data in any of those would bloat the model's context, the database row, and the UI's plain-text trace.

**Consequence for FR-004 ("displayed... in the same way")**: the visual/storage mechanism is identical — same `Image::storeFromBase64`, same `imageable` morph, same `msg.image_url` rendering path `ChatMessage.jsx` already has, zero new frontend code. The one difference from the manual command is that the picture and the model's comment about it land in two separate assistant bubbles (image-only, then text) instead of one combined bubble — an accepted, minor divergence, not a functional gap, and it's what naturally happens for any other tool's result plus the model's follow-up text today.

**Alternatives considered**: Deferring image attachment until after `run()` returns, by having the tool expose its last-generated image for the controller to pull out and attach to its own final message. Rejected — it re-introduces the multi-image problem (only the *last* generated image would have a message to attach to under this scheme unless the controller loops over every image the tool produced, which is the same amount of code as just letting the tool create its own carrier message immediately) for no benefit, since a `Message` with empty `content` renders identically to one with real content once an image is attached.

## 4. Reconciling the tool-call timeout with image generation's own timeout

**Decision**: Add `timeoutSeconds(): int` to the `AgentTool` interface. `GetCurrentDatetimeTool` and `BasicCalculatorTool` both return `config('agent.tool_timeout')` (today's global default, unchanged behavior for them). The new tool returns the *actual resolved* image-gen timeout for this specific assistant — `ImageGenModel->config['timeout'] ?? config('ai.image_gen.timeout')` (exposed via `ImageGenerationService::resolveTimeoutFor()`) — plus a fixed 30-second buffer for the prompt-enhancement LLM call and image storage I/O that happen around the provider call itself. `AgentLoopRunner::executeWithTimeout` calls `$tool->timeoutSeconds()` instead of reading `config('agent.tool_timeout')` directly.

**Rationale**: The problem is real, not hypothetical — `config('agent.tool_timeout')` defaults to 60s while `config('ai.image_gen.timeout')` defaults to 120s, so an image tool call would already be killed by `pcntl_alarm` before a normal successful generation completes, let alone one using a per-assistant model configured with an even longer timeout. A single global number can't serve both an instant in-process calculation and a slow external HTTP call correctly. Deriving the tool's timeout from the *resolved* per-assistant configuration (not the global default) is what actually fixes the mismatch in every case, not just the default one — a per-assistant `ImageGenModel` with a longer configured timeout would otherwise still get killed early. Adding this as an interface method (not an `instanceof` special case for one tool) is justified under Constitution Principle VII specifically because there are now two real callers with genuinely different timing needs, which is exactly the "second real caller" trigger the principle names for introducing shared structure — it is not speculative.

**Alternatives considered**: Raising the single global `agent.tool_timeout` default high enough to cover image generation. Rejected — it would loosen the hang-detection ceiling for every tool, including the two instant ones, for a problem specific to one slow tool. A new dedicated `config/agent.php` key (e.g. `image_tool_timeout`) duplicating `ai.image_gen.timeout`. Rejected — two independently-set config values for the same underlying budget will drift out of sync (someone raises one and not the other); deriving from the existing `ai.image_gen` configuration directly is the single source of truth.

## 5. Retry budget for a slow, costly external call

**Decision**: No change — the image tool uses the same `config('agent.tool_retry_attempts')` (default 3) as every other tool, each attempt bounded by its own fresh `timeoutSeconds()` window (existing behavior of `executeWithRetries`, unchanged).

**Rationale**: A per-tool retry override was considered specifically because retrying a failing external, paid API call three times is a real cost concern in a way retrying an in-process calculator never is — but it would be a second new `AgentTool` interface method in the same feature, for a concern the spec never raised (no success criterion or requirement mentions generation cost or retry tuning). Constitution Principle VII cuts the other way here: this isn't a second real caller with a demonstrated need yet, it's a hypothetical future one. The known consequence — worst case, one image-generation tool call can take up to `tool_retry_attempts × (resolved image timeout + 30s)` before failing, roughly 6-7 minutes at current defaults, synchronously blocking the request — is an extension of the exact risk 001's plan already accepted for the loop's synchronous execution model in general, not a new one this feature introduces.

**Alternatives considered**: A `retryAttempts(): int` method on `AgentTool`, mirroring `timeoutSeconds()`, defaulting to the global config for existing tools and returning `1` (no retry) for the image tool. Set aside for the reason above; revisit if real usage shows repeated-failure cost is an actual problem, not a projected one.

## 6. Gating tool availability on image-gen configuration (FR-005)

**Decision**: `ImageGenerationService::isAvailableFor(AssistantUser $assistantUser): bool` attempts `ImageGenManager::forAssistantUser($assistantUser)` in a try/catch, returning `false` only if it throws `InvalidArgumentException` (the one case `ImageGenManager::fromConfig()` throws today — no URL configured anywhere, per-assistant or global). `ConversationController::sendMessage` only adds `ImageGenerationTool` to the tools array passed into `AgentLoopRunner` when this returns `true`; the same array literal already other tools are added to unconditionally (`ConversationController.php:254-257`).

**Rationale**: `ImageGenManager::forAssistantUser` already encodes exactly the "is there a usable image-gen configuration" check the manual command silently relies on (it never throws for a normally-configured install, since `config/ai.php`'s `image_gen.url` ships with a default) — reusing it instead of inventing a second, parallel notion of "configured" keeps there being exactly one source of truth for that question.

**Alternatives considered**: A dedicated boolean flag on `Assistant` or `AssistantUser` (e.g. `image_generation_enabled`) set explicitly, mirroring `AiModel.supports_tools` (research.md #6 in 001-agentic-task-loop). Rejected as unnecessary bookkeeping — unlike tool-calling support (which some models silently ignore rather than error on, per 001's research.md #6), whether image generation is configured is already reliably knowable up front without a runtime probe, so an explicit flag would just duplicate state that already exists.

## 7. Naming and parameters

**Decision**: Tool name `generate_image`, one required string parameter `prompt` (the raw description, enhanced internally exactly like `/create-image`'s argument is today). Full contract in contracts/generate-image-tool.md.

**Rationale**: Matches the existing `snake_case` naming convention (`get_current_datetime`, `basic_calculator`) and mirrors the manual command's own single free-text argument — no new parameter shape to design.

## 8. Testing strategy

**Decision**: Pest feature tests fake both the LLM HTTP calls (`Http::fake()`, sequencing a `tool_use`/`tool_calls` response for `generate_image` followed by a final-answer response) and the image-gen provider's HTTP call, following the exact pattern `001-agentic-task-loop`'s `AgentLoopSingleToolCallTest.php` already established for `basic_calculator`/`get_current_datetime`. A dedicated timeout test (mirroring `AgentLoopToolTimeoutTest.php`) asserts `ImageGenerationTool::timeoutSeconds()` reflects the resolved per-assistant configuration, not the global `agent.tool_timeout` default.

**Rationale**: Matches Constitution Principle VI and the project's already-established convention for this exact kind of feature, set one spec ago.
